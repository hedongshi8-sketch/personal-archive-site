# 《我的修仙日常》UI/UX信息呈现参考校准包

## 任务信息

- 项目ID：`P-20260802-我的修仙日常`
- 任务编号：`REV-20260804-04`
- 任务类型：game-uiux-reference-calibration / information-presentation
- 模块：资料模块
- 结论：本项目是单机独立游戏，主画面必须服务游玩、观察和决策，不允许把开发调试变量当成玩家HUD。

## 0. 本轮校准结论

当前 Godot Demo 的 `state_label` 是典型“变量总账式HUD”：

```text
形态 | 心境 | 显形符 | 爆炸符 | 传音 | 理解 | 灵草 | 灵石 | 林小满关系
```

这些信息并非全部不该存在，而是不该以常驻文字总账形式铺在主画面。成熟单机游戏通常把信息拆进四层：

1. **主游玩HUD**：只放当下行动必须知道的少量信息。
2. **短时提示**：获得、危险、状态变化出现数秒后消失。
3. **场景反馈**：让世界对象发生变化，玩家从画面中读懂系统。
4. **主动菜单 / 札记 / 背包 / 地图**：长期状态由玩家主动查看。

调试信息可以保留，但必须进入开发开关，默认玩家画面不显示。

## 2. 单机游戏信息呈现的核心原则

### 2.1 HUD不是系统清单

HUD应该回答：“玩家此刻做决策需要什么？”而不是“项目里有哪些变量？”

对本项目来说，默认主画面只应常驻：

- 当前可交互对象提示，例如 `E：洞府师札`。
- 当前选中的能力/符箓小图标。
- 立刻影响行动的危险或限制，例如元神离体即将失控、心境临界。
- 极少量核心资源，如果它直接影响当前动作。

不应常驻：

- 已解锁 / 未解锁能力列表。
- 全部资源数量。
- NPC关系值。
- 剧情理解状态。
- 形态、心境、传音、理解等调试变量。

### 2.2 能力状态要通过世界和动作表达

“显形符已解锁”不是要挂在屏幕上，而是：

- 玩家获得时出现短时反馈：符纸发亮、音效、短句。
- 后续进入“符箓匣 / 修行札记”。
- 当靠近可显形对象时，符箓图标微亮或场景纹路轻闪。
- 使用后世界对象变化：隐纹显现、空气墙变成可读符阵。

### 2.3 主动菜单承载长期信息

长期状态不是删掉，而是迁移：

| 信息 | 应进入 |
| --- | --- |
| 已会符箓 | 符箓匣 |
| 功法残页 / 修行理解 | 修行札记 |
| 灵草、灵石、丹药 | 行囊 |
| NPC印象、传音碎片 | 关系录 / 传音札 |
| 已发现异常点 | 地图标记 |
| 所有调试变量 | Debug Overlay，默认关闭 |

Godot 实现上，HUD 可用 `CanvasLayer` 承载，但 CanvasLayer 是分层绘制工具，不等于应该把所有状态都画出来。Godot 官方 UI 文档强调 UI 基于 Control 节点和布局控件；本项目应把 HUD、菜单、短时提示、Debug Overlay 拆成不同 UI 层。

## 4. 主HUD / 主动菜单 / 场景反馈 / 教学 / 调试边界

### 4.1 主游玩HUD

只允许放：

- 交互提示：靠近对象时显示 `E：对象名`。
- 当前能力槽：一个小图标，而不是能力清单。
- 危险临界：元神离体倒计时、心境过低警示。
- 获得反馈：`获得：显形符残页`，2-3秒后淡出。

### 4.2 主动菜单

按玩家主动查看组织：

- `修行札记`：规则发现、功法残页、修行理解。
- `符箓匣`：显形符、爆炸符、护体符，含简短说明。
- `行囊`：灵草、灵石、丹药、材料。
- `地图`：已发现异常点，不自动揭示未探索目标。
- `关系录`：NPC印象、约定、传音碎片。

### 4.3 场景反馈

- 显形符：隐藏纹路发光，空气墙变符阵，机关节点显露。
- 爆炸符：裂岩震动、碎石留场、路径打开。
- 护体符：危险靠近时护罩短暂出现。
- 元神出窍：画面降噪、角色半透明、只显示灵性对象。
- 传音：肉身听断裂片段；元神状态听到完整句，声音方向指向来源。

### 4.4 教学呈现

教学目标不是把系统写满屏，而是让玩家通过场景试错建立理解：

1. 第一次只给移动和一个互动对象。
2. 第一个符箓用一个可见异常物件教学，例如“雾墙旁符纸微亮”。
3. 失败反馈也要可读，例如未学显形符时机关只闪一下。
4. 每条说明只在需要时出现，出现后淡出。
5. 关键规则进入札记，玩家需要时再主动查看。

### 4.5 调试信息

保留给开发，但必须默认关闭：

- 可用 `F3` 或 Debug Mode 切换。
- 显示变量总账、碰撞范围、当前 nearby、任务标志位。
- 不进入验收截图，不进入玩家默认启动画面。

## 5. 参考作品的可借鉴方式

### 《塞尔达传说：旷野之息》

参考点不是“照搬HUD”，而是学习它如何让能力和环境对象互相响应。能力状态不需要用文字解释全部变量；玩家通过火、电、风、重量、天气和物体反应理解世界。对本项目的转译是：符箓、元神、传音都要落在对象反应上。

### 《星露谷物语》

生活模拟的长期信息多，但主游玩画面克制，背包、关系、地图、日程等由菜单承载。玩家在地块、村庄和矿洞中行动时，界面不应变成“所有系统进度面板”。对本项目的转译是：资源、关系、札记应主动查看，主画面只服务当前行动。

### 《波西亚时光》

工坊、订单、制作链很多，但玩家通过工作台、委托板、地图和角色对话进入系统。对本项目的转译是：门派委托和修行记录应有空间入口，例如告示牌、札记、符匣，而不是常驻在屏幕。

### 《大侠立志传》

单机RPG可承载大量人物、关系、物品和任务，但这些信息通常进入菜单、对话、地图和角色界面。对本项目的转译是：关系值不该常驻HUD，应通过NPC称呼、对话选项、关系录表达。

### 高质量UI分析共识

Game Developer 等分析文章反复强调 HUD 要克制、情境化、服务当下注意力；论坛和博客观点只能作启发，但可支持一个共识：**信息越多，越需要分层；越底层的系统变量，越不该直接暴露给玩家。**

## 6. 给系统体验模块 `REV-20260804-05` 的直接原则

1. 先写信息架构，不先写HUD文案。
2. 主HUD只显示当下行动必要信息。
3. 长期状态必须进入主动菜单。
4. 能力获得用事件表达，不能用“已解锁/未解锁”常驻列表表达。
5. 能力可用性用图标状态、对象反应、动作反馈表达。
6. 显形符、爆炸符、护体符、元神、传音都必须有场景反馈方案。
7. 教学使用观察、异常、短提示、失败反馈和札记沉淀。
8. 调试变量必须进入 Debug Overlay，默认关闭。
9. 默认运行截图不得出现变量总账。
10. 所有UI都要回答“玩家此刻为什么需要知道它？”

## 7. 下一轮写作建议

系统体验模块下一轮文档应拆成：

1. 主游玩HUD规格。
2. 主动菜单规格：修行札记、符箓匣、行囊、地图、关系录。
3. 场景反馈规格：显形、爆炸、护体、元神、传音。
4. 教学呈现规格：首5分钟如何教移动、互动、显形符。
5. Debug Overlay规格：哪些变量保留给开发。
6. 一票否决项：主画面变量总账、已解锁列表、文字堆屏、网页问答式交互。

## 8. 结论

《我的修仙日常》的 UI/UX 问题不是“HUD还不够完善”，而是信息架构错误。要把“系统变量”改写成“玩家体验到的世界反馈”：主画面克制，菜单主动，反馈落在场景，教学靠观察和试错，调试信息默认隐藏。
